# Восстановление пароля: требования к Auth API

**Дата:** 2026-11-11
**Статус:** Черновик для команды бэкенда
**Макет:** https://claude.ai/artifact/PHeB3SfALtr8tVDrfQ7nRa (ряд «Восстановление пароля»: экраны 4–6 и телефон)
**Клиенты:** math-on-canvas (Next.js, сайт и каталог) и math_poster_editor (редактор). Оба ходят в один Auth API.

## Что есть сейчас

Фронтенд вызывает Auth API напрямую из браузера (`NEXT_PUBLIC_AUTH_API_URL`, `credentials: 'include'`, сессия в cookies):

| Метод | Путь | Тело → ответ |
|---|---|---|
| POST | `/auth/signup` | `{ email, password, displayName }` → `{ confirmationRequired, email }` |
| POST | `/auth/confirm-signup` | `{ email, code }` → `{ confirmed }` |
| POST | `/auth/resend-code` | `{ email }` → `{ sent }` |
| POST | `/auth/signin` | `{ email, password }` → `{ success }` + cookies сессии |
| GET | `/auth/me` | → `UserProfile` |
| POST | `/auth/refresh` | → `{ expiresIn }` |
| POST | `/auth/logout` | — |
| GET | `/auth/login?redirect_uri=…` | вход через Google (редирект) |

Формат ошибки: HTTP 4xx и тело `{ "error": "<code>", "message": "…", "request_id": "…" }`. Фронтенд показывает пользователю перевод по `error`. Сейчас он знает коды `email_already_exists`, `invalid_confirmation_code`, `unauthorized`, `user_not_confirmed`, `rate_limit_exceeded`, `password_too_weak`.

Методов для восстановления пароля нет. На фронтенде ссылка «Забыли пароль?» переведена, но не показывается.

## Пользовательский сценарий

1. На экране входа пользователь нажимает «Забыли пароль?». Открывается экран 4, почта подставлена из формы входа.
2. «Отправить код» → **RP-1**. Пользователь видит экран 5: «Если аккаунт с этой почтой существует, мы отправили на неё код».
3. Пользователь вводит 6-значный код из письма и новый пароль, нажимает «Сохранить и войти» → **RP-2**.
4. Экран 6 «Пароль изменён. Вы вошли как …». Пользователь уже авторизован, окно закрывается.

Повторная отправка кода повторяет RP-1. Кнопка доступна через 60 с, на экране идёт обратный отсчёт.

## RP-1 (P0). Запрос кода

`POST /auth/forgot-password`

```json
{ "email": "anna@school.ru", "lang": "ru" }
```

- `email`: обязательное поле. Перед поиском аккаунта обрезать пробелы и привести к нижнему регистру, так же как при входе.
- `lang`: необязательное, одно из `en | ru | es | de`. Язык письма. Если не передано, брать язык аккаунта, а если и его нет — `en`.

**Ответ 200, одинаковый в любом случае:**

```json
{ "sent": true, "codeLength": 6, "expiresIn": 3600, "resendAfter": 60 }
```

- Ответ не должен выдавать, существует ли аккаунт. Тело, статус и время ответа одинаковые для существующей и несуществующей почты, иначе через форму можно перебирать чужие адреса. Письмо отправлять асинхронно, чтобы время ответа не зависело от отправки.
- `expiresIn` и `resendAfter` задаются в секундах. Фронтенд берёт их для текстов («код действует 1 час») и для таймера и ничего не захардкодит.

**Что делать в зависимости от состояния аккаунта:**

| Аккаунт | Что сделать |
|---|---|
| Есть, почта подтверждена | Сгенерировать код и отправить письмо со сбросом пароля. |
| Есть, почта не подтверждена | Тоже отправить код сброса. Успешный RP-2 заодно подтверждает почту: код доказывает, что пользователь владеет ящиком. |
| Есть, только вход через Google, пароля нет | Код не отправлять. Отправить письмо «Вы входите через Google» со ссылкой на сайт. Ответ тот же. |
| Нет | Ничего не отправлять. Ответ тот же. |

**Ошибки:**

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `invalid_email` | Почта пустая или некорректна по формату (новый код) |
| 429 | `rate_limit_exceeded` | Превышен лимит, см. «Безопасность». Добавить заголовок `Retry-After` в секундах. |

## RP-2 (P0). Новый пароль по коду

`POST /auth/reset-password`

```json
{ "email": "anna@school.ru", "code": "730926", "newPassword": "Kvadrat-2026" }
```

**Ответ 200:**

```json
{ "success": true }
```

Вместе с ответом выставить **cookies сессии так же, как при `/auth/signin`**: тот же набор, атрибуты и домен. После этого фронтенд вызывает `/auth/me` и показывает «Вы вошли как …».

> Если сразу выдавать сессию нельзя, вернуть `{ "success": true, "signedIn": false }` без cookies. На макете есть запасной вариант экрана 6: «Войдите с новым паролем», и почта подставляется в форму входа. Основной вариант всё же автоматический вход.

**Ошибки:**

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `invalid_reset_code` | Код неверный, истёк, уже использован или для этой почты кода нет (в том числе если аккаунта нет). Все эти случаи — один код ошибки (новый). |
| 400 | `reset_attempts_exceeded` | Для этого кода исчерпаны попытки ввода (5). Код аннулирован, нужен новый через RP-1 (новый код ошибки). |
| 400 | `password_too_weak` | Пароль не проходит политику. Код уже используется при регистрации. |
| 429 | `rate_limit_exceeded` | Слишком много запросов. Добавить `Retry-After`. |

Если ошибка `password_too_weak`, код сброса **не сгорает** и попытка не засчитывается: пользователь исправит пароль и отправит форму снова.

## RP-3 (P1). Уведомление о смене пароля

После успешного RP-2 отправить на почту аккаунта письмо «Пароль изменён» на языке из RP-1. В письме: дата и время, примерное устройство или браузер, и что делать, если пароль менял не владелец (адрес поддержки).

## RP-4 (P2). Политика пароля одним источником

Фронтенд проверяет пароль сам: не меньше 8 символов, заглавная буква, строчная, цифра, спецсимвол. Это правило продублировано у него в коде. Желательно отдавать политику через `GET /auth/password-policy`:

```json
{ "minLength": 8, "requireUppercase": true, "requireLowercase": true, "requireDigit": true, "requireSymbol": true }
```

Тогда при изменении политики на бэкенде фронтенд не начнёт пропускать пароли, которые сервер потом отклонит. Политика при регистрации и при сбросе обязана быть одинаковой.

## Безопасность

- **Код:** 6 цифр из криптографически стойкого генератора. Хранить только хеш. Действует 60 минут, используется один раз. Новый запрос RP-1 аннулирует предыдущий код.
- **Попытки:** не больше 5 неверных вводов на один код, затем `reset_attempts_exceeded`.
- **Лимиты RP-1:** на одну почту не чаще 1 раза в 60 с и не больше 5 раз в час. С одного IP не больше 20 раз в час. Почту для подсчёта лимитов брать после нормализации.
- **Лимиты RP-2:** с одного IP не больше 30 запросов в час.
- **После смены пароля** отозвать все refresh-токены и сессии аккаунта, кроме только что выданной: остальные устройства выходят из аккаунта. Об этом сказано на экране 5.
- **Логи:** не писать в них коды и пароли. События `password_reset_requested` и `password_reset_completed` фиксировать в аудите с `request_id`.
- **CORS и cookies:** как у `/auth/signin`, то есть разрешённые origin сайта и редактора и `Access-Control-Allow-Credentials: true`.

## Письмо с кодом

- Тема: «Код для смены пароля — Math on Canvas», локализована.
- Код набран крупным моноширинным шрифтом. В тексте указан срок действия («1 час») и сказано, что если сброс запрашивал не пользователь, письмо можно проигнорировать.
- Ссылка с кодом в письме **не нужна**: сценарий целиком проходит в окне на сайте.
- Отправитель и оформление такие же, как у письма с подтверждением регистрации.

## Критерии приёмки

1. RP-1 для существующей и несуществующей почты возвращает одинаковые статус и тело, а время ответа отличается не больше чем на 100 мс (медиана).
2. Письмо с кодом приходит на языке из `lang`. Код из письма принимается в RP-2.
3. После RP-2 с верным кодом:
   - старый пароль перестаёт работать в `/auth/signin`;
   - новый пароль работает;
   - `/auth/me` с выданными cookies возвращает профиль;
   - refresh-токен другого устройства получает 401.
4. Повторное использование того же кода → `invalid_reset_code`.
5. Шестой неверный ввод → `reset_attempts_exceeded`, и после этого верный код тоже не принимается.
6. Второй RP-1 раньше чем через 60 с → 429 с `Retry-After`.
7. Слабый пароль → `password_too_weak`, и затем тот же код с сильным паролем проходит.
8. Аккаунт с неподтверждённой почтой после RP-2 входит без шага `confirm-signup`.
9. Для аккаунта только с Google код не приходит, приходит письмо про вход через Google.
10. Эндпоинты описаны в OpenAPI сервиса с примерами запросов, ответов и ошибок.

## Что сделает фронтенд (для сведения)

- `authApiClient.forgotPassword(email, lang)` и `authApiClient.resetPassword(email, code, newPassword)`.
- Новые виды окна: `forgotPassword`, `resetPassword`, `resetDone`. Ссылка «Забыли пароль?» на экране входа.
- Перевод новых кодов `invalid_email`, `invalid_reset_code` и `reset_attempts_exceeded` в `mapAuthError`, тексты в четырёх локалях.
- Таймер повторной отправки берётся из `resendAfter` или `Retry-After`.
- Добавить `/auth/forgot-password` и `/auth/reset-password` в `SKIP_PATHS` перехватчика 401: на эти запросы не нужно пытаться обновить токен.
- Локальный прокси `/auth/[...path]` уже пропускает любые POST, так что для разработки на staging ничего не нужно.

## Открытые вопросы к бэкенду

1. Сервис построен на AWS Cognito? Коды `user_not_confirmed` и `confirm-signup` на это похожи. Если да, RP-1 и RP-2 ложатся на `ForgotPassword` и `ConfirmForgotPassword`. Но нужно проверить, что в Cognito включено «Prevent user existence errors», и решить, как после `ConfirmForgotPassword` выдать сессию: например, следом вызвать `InitiateAuth` с новым паролем.
2. Можно ли выдавать сессию сразу в RP-2? Если нет, фронтенд включит запасной вариант экрана 6.
3. Подходит ли подтверждать почту через сброс пароля для неподтверждённых аккаунтов, или нужно сначала требовать `confirm-signup`?
4. Нужна ли пользователям, которые входят только через Google, возможность задать пароль? В этом задании такой возможности нет, им приходит информационное письмо.
